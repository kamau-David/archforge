  ## Known Risk Areas (Ranked by Severity)                                                                              

  ### 🔴 Critical                                                                                                       

  1. **Logic bug in `tryCreateUserRecord()`** — `lib/main.dart`                                                         
     Condition is `userName != null || userName.length != 0`. The `||` should be `&&`. If `userName` is `null`,         
evaluating `.length` will throw a `Null check operator used on a null value` error at runtime.                          

  2. **Unhandled async errors in feed assembly** — `functions/src/getFeed.ts`                                           
     `compileFeedPost()` uses `.then().catch()` but errors inside the pipeline are silently swallowed. A broken post    
query will cause the HTTP response to be missing data with no error surfaced to the caller.                             

  3. **No null safety** — `lib/models/user.dart` (and the wider `lib/` module)                                          
     All `User` fields are non-nullable `final` with optional constructor parameters and no defaults. The codebase      
predates Dart sound null safety (pre-2.12). A missing Firestore field will cause a runtime cast error at                
`User.fromDocument()`.                                                                                                  

  ### 🟡 Medium                                                                                                         

  4. **`sendNotification` is fire-and-forget** — `functions/src/notificationHandler.ts`                                 
     The returned `Promise` is not awaited in `notificationHandlerModule`, meaning FCM delivery failures are silently   
ignored and would normally trip the `no-floating-promises` TSLint rule.                                                 

  5. **`res` passed but unused in `getAllPosts` / `getUserPosts`** — `functions/src/getFeed.ts`                         
     The response object is threaded through these functions but only `getFollowing` actually uses it for error         
responses. Errors deeper in the pipeline do not terminate the HTTP response, risking a hanging request.                 

  6. **Mutable global state** — `lib/main.dart` (`currentUserModel`)                                                    
     The logged-in user is a top-level mutable global with no state management library. Concurrent writes from different
widgets (e.g. `edit_profile_page.dart` and `profile_page.dart`) are unsynchronized.                                     

  7. **Likes and follows stored as maps** — `lib/image_post.dart`, `lib/profile_page.dart`                              
     `Map<userId, bool>` is stored directly on the post/user document. Firestore documents have a 1 MB limit;           
high-follower accounts will eventually hit it.                                                                          

  ### 🟢 Low                                                                                                            

  8. **Deprecated Flutter APIs** — `lib/` (multiple files)                                                              
     `FlatButton`, `OutlineButton`, `buttonColor`, and `BottomNavigationBarItem.title` are all removed in recent Flutter
SDK versions. The app will not compile against a current Flutter SDK without migration.                                 

  9. **`functions` import is unused in `getFeed.ts`** — `functions/src/getFeed.ts`                                      
     Only `admin` is used; the `functions` import is dead code.                                                         

  10. **EOL runtime and old SDKs** — `functions/package.json`                                                           
      Targets Node 8 (end-of-life) with `firebase-admin ^6` and `firebase-functions ^2`. Modern Cloud Functions runtimes
require Node 18+.

Cloud Functions

1. notificationHandler\

  • Trigger: Firestore onCreate on path /insta_a_feed/{userId}/items/{activityFeedItem}
  • Logic (notificationHandlerModule):
    1. Reads the newly created activity feed item (snapshot.data()).
    2. Fetches the target user's document from insta_users/{userId}.
    3. Looks up androidNotificationToken on that user document.
    4. If a token exists, calls sendNotification().
  • sendNotification()\ builds an FCM message with title/body based on the activity type:
    ┌─────────┬────────────────────────────────────┬─────────────────────────────────────────────┐
    │ type │ title │ body │
    ├─────────┼────────────────────────────────────┼─────────────────────────────────────────────┤
    │ comment │ "New Comment" │ "{username} commented on your post: {text}" │
    ├─────────┼────────────────────────────────────┼─────────────────────────────────────────────┤
    │ like │ "{username} liked your post" │ (empty) │
    ├─────────┼────────────────────────────────────┼─────────────────────────────────────────────┤
    │ follow │ "{username} started following you" │ (empty) │
    └─────────┴────────────────────────────────────┴─────────────────────────────────────────────┘
  • Sends via admin.messaging().send(message).

────────────────────────────────────────────────────────────────────────────────

2. getFeed\

  • Trigger: HTTPS request (functions.https.onRequest)
  • Logic (getFeedModule):
    1. Reads uid from the query string (req.query.uid).
    2. Calls getFollowing(uid)\ — fetches the user's insta_users/{uid} document, extracts the following map (keys where
      value is true), returns a list of followed UIDs.
    3. Calls getAllPosts(following, uid)\ — iterates over all followed users plus the requesting user, calling
      getUserPosts(userId)\ for each.
    4. getUserPosts()\ queries insta_posts where ownerId == userId, ordered by timestamp.
    5. Flattens all per-user post arrays into a single list and sends it in the HTTP response.

lib/models — Overview

user.dart\

Defines the User data model, which maps a Firestore document to a Dart object.

Constructor

  • All fields are named optional parameters passed to a const constructor.

Factory

  • User.fromDocument(DocumentSnapshot document)\ — deserializes a Firestore DocumentSnapshot\ into a User instance. It maps field names directly (e.g. document['email']) and uses document.id for the Firestore document ID.

Notable Observations

  1. No null safety — all fields are non-nullable final with no default values, and all constructor parameters are
    optional. This indicates the code predates Dart's sound null safety (pre-Dart 2.12 style).
  2. Untyped Maps — followers and following are typed as Map (no generics). In practice these are likely Map<String, bool> (Firestore social graph pattern).
  3. No toMap() / serialization — there is no method to serialize User back to a Firestore document. Writes to Firestore
    are likely handled elsewhere in the codebase.
  4. Single model — the module only models a User. Other entities (e.g. posts, comments) are presumably handled either
    inline or via raw DocumentSnapshot access elsewhere.
