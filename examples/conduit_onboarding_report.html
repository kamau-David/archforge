notification settings, theme, locale, transport mode, password changes, and many more control IDs.

heuristics), and system UI overlay sync.

Key Architectural Observations

  1. Host-port inversion: conduit_core defines abstract ports; lib/platform/ binds Flutter plugin implementations at
    startup. This keeps core logic testable without Flutter.
  2. Single ProviderContainer: All Riverpod state lives in one container built in main() with explicit overrides for every platform adapter.
  3. Backend-agnostic router: The router supports three primary backend modes — OpenWebUI, Hermes-only, and Direct
    Connections — with independent routing guards for each.
  4. Native sheet bus: The entire iOS native settings sheet is driven through a single NativeSheetBridge event stream
    handled in _ConduitAppState._handleNativeSheetEvent, dispatching to ~40 distinct control IDs.
  5. Feature isolation: Each features/ vertical is self-contained but can read shared providers from conduit_core and
    shared UI from lib/shared/.

Key Design Patterns

  1. Riverpod + keepAlive — Long-lived background providers are kept alive by subscribing to them (not watching),
    preventing disposal while the app is running.
  2. Frame-budgeted startup queue — Heavy initialization is spread across frames to avoid startup jank.
  3. Generation counters (ABA fences) — Used in both MediaUploadController and ImageAttachmentCacheStore to prevent race
    conditions between cancellation and restart of the same path/key.
  4. Auth epoch scoping — Image caches and upload receipts use object-identity auth-session epochs to prevent
    cross-account content leakage without losing disk-cache persistence across restarts.
  5. Auth-boundary cleanup — A two-phase snapshot → retire pattern safely tears down the previous session's composer state without racing a rapid re-authentication.

Overview

lib/platform is the Flutter app's platform-adaptation layer — the seam between conduit_core (the platform-agnostic
business logic) and the concrete runtime environment (iOS, Android, web, native OS services).

It has two distinct categories of files:

  1. Port implementations — concrete Flutter/plugin bindings for abstract conduit_core interfaces (*Port classes)
  2. Platform coordinators & services — heavier orchestrators that own a named channel or Riverpod provider and handle
    OS-level integration (share receiving, App Intents, CarPlay, home-screen widgets, etc.)

The most complex file. Handles iOS Siri/Shortcuts (App Intents) via AppIntentFlutterApi (Pigeon).

- AppIntentCoordinator (Riverpod @keepAlive) — the live handler. Implements askChat, sendText, sendUrl, sendImage,

Design Principles Observed

  1. Ports isolate Flutter dependencies from conduit_core — no flutter/ imports in core.
  2. Every mutation through a serialization tail — both WebViewCookieHelper and AppIntentInvocationLedger use a
    _tail.then() chain to prevent concurrent state corruption.
  3. Unavailable handlers over null — Pigeon slots always have a fallback responder (_UnavailableAppIntentHandler) rather than being unset, preventing native crashes.
  4. Generation counters for scene/clear races — CarPlayCoordinator uses _sceneGeneration, WebViewCookieHelper uses
    _fullClearGeneration to discard stale completions.
  5. Graceful MissingPluginException handling — headless/test environments silently degrade (IosDisplayBoost,
    CarPlayCoordinator, AndroidImeInsetResync).

tool/ Module Overview

The tool/ directory is a collection of standalone Dart developer scripts — none are part of the shipping app. They are
invoked with dart run tool/<script>.dart and serve four distinct purposes:

────────────────────────────────────────────────────────────────────────────────

1. Architecture Enforcement

check_package_boundaries.dart\

The most important CI script. Enforces a strict layered architecture across the monorepo with three independent checks:

  • _scanForTransitiveFlutter — Scans packages/conduit_core/lib and walks package_config.json to find any package that
    transitively depends on the Flutter SDK. This catches sneaky dependencies that aren't in any named deny-list.
  • Web-safe packages — conduit_protocol, conduit_theme, conduit_markdown must stay compilable via dart compile js. Bans
    dart:io, dart:ffi, package:dio, package:drift, etc.
  • Flutter-free directories — lib/core/database, lib/core/models, lib/core/sync (and two individual files) must not
    import Flutter, so they can run inside the conduitd sidecar daemon.
  • _scanDesktopUi — The desktop renderer (apps/desktop_ui) may only import what its own pubspec.yaml declares, and may
    never declare dio, drift, conduit_core, or Flutter regardless. Derived from the pubspec (allow-list), not a deny-list.

────────────────────────────────────────────────────────────────────────────────

2. Code Splitting / Refactoring Tools

These are one-shot migration assistants for restructuring large Dart files without manual line counting.

list_top_level_declarations.dart\

Parses a Dart library with the analyzer package and emits a TSV of startLine / endLine / kind / name for each top-level declaration. Used to plan part file splits.

list_class_members.dart\

Similar, but drills into a named class and emits its members as TSV — including a callees column (other members
referenced in the body) to identify what needs an abstract declaration on a shared base class.

split_into_parts.dart\

Consumes a TSV plan from list_top_level_declarations.dart and splits a library into part files. Uses two safety gates
before touching any file:
- _assertNothingLost — every non-blank line of the original must appear exactly once across all outputs.
- _assertStillParses — all output files are fed to the analyzer parser; a bad range that is off by one would otherwise
produce silently broken code.

split_class_into_mixins.dart\

Like split_into_parts.dart but for class members specifically, wrapping each output group in its own mixin ... on ...
declaration. The design rationale (mixin vs. extension vs. delegation) is documented inline — mixins are chosen because extension methods resolve statically and would silently bypass 60+ fakes and 9 mocks in the test suite.

────────────────────────────────────────────────────────────────────────────────

3. Test Migration

migrate_core_tests.dart\

Moves tests from test/ into packages/conduit_core/test/ once the code they test has been extracted to conduit_core. Key design decisions:
- Builds a dependency graph including relative imports, not just package: URIs (an earlier version missed helpers and
broke 18 files).
- Uses a fixed-point shrink algorithm to determine the largest set of files that can move without leaving dangling
edges.
- Rewrites package:flutter_test → package:test (only when no testWidgets/WidgetTester/etc. are used).
- Run with --apply to execute; without it, it is a dry run.

────────────────────────────────────────────────────────────────────────────────

4. Asset & Localization Validation

validate_arb_locales.dart\

Validates all .arb locale files under lib/l10n/:
- Groups files into namespaces by filename prefix (app_, desktop_), so the mobile and desktop catalogs are validated
against their own English templates.
- Checks: missing keys, orphaned keys, placeholder parity.
- Also does a best-effort unused-key scan across lib/ and apps/desktop_ui/lib/.

verify_arb_descriptions.dart\

Checks every non-meta key in every English *_en.arb template has a @key entry with a non-empty description field.

release_notes_validator.dart\

A library (not a runnable entrypoint) that validates bundled release-note JSON assets and ARB shell keys. Checks: valid JSON, required schema fields (version, title, intro, bullets), sorted/unique versions, known icon names, locale parity
(same version set and bullet counts as the English template).

validate_release_notes.dart\

Thin CLI wrapper that calls validateReleaseNotes() from the library above. Usage: dart tool/validate_release_notes.dart --version x.y.z.

────────────────────────────────────────────────────────────────────────────────

5. Test Harnesses

direct_mcp_app_fixture.dart\

A minimal HTTP server that logs every inbound request as JSONL and serves a redirect or a plain "captured" response.
Used as the remote endpoint for MCP app containment security tests.

direct_mcp_app_harness.dart\

A Flutter app harness for testing the DirectMcpAppView widget. Renders a deliberately hostile HTML page that attempts
every known exfiltration vector — fetch, XHR, <img>, <iframe>, <form>, popups, custom URL schemes, clipboard writes,
camera/microphone/geolocation access, service worker registration — and verifies the containment layer blocks all of
them.

────────────────────────────────────────────────────────────────────────────────

6. Platform Code Generation

pigeon_codegen/bin/generate.dart\

Runs Pigeon\ to regenerate platform-channel bindings from pigeons/conduit_platform_apis.dart\, then post-processes the
Kotlin output to strip trailing whitespace and work around a Pigeon 27.3 narrowing bug in nullable error replies.
